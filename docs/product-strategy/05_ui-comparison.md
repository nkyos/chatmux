# UI 形態の比較検討

## 前提

- セッション選択時は Claude Code のターミナル画面をそのまま表示したい
- セッション一覧にプロジェクト名、最新返信時間、状態を表示したい
- 返信が来たら通知がほしい

## PTY 埋め込みが最大の技術課題

「ターミナル画面をそのまま表示」= ターミナルエミュレータの組み込みと同義。
各 UI 形態でこれをどう実現するかが分かれ道。

## 比較

### 案 1: tmux バックエンド + TUI フロントエンド

tmux にセッション管理・PTY 描画を任せ、chatmux は上にセッション管理 UI を被せる。

**メリット:**
- tmux の PTY 管理は枯れていて信頼性が高い
- 開発コストが最も低い
- ターミナル完結（開発者に馴染む）

**デメリット:**
- サイドバー等の UI の自由度に制約
- tmux に依存（ユーザーが tmux をインストールする必要あり）
- ネイティブ通知は別途工夫が必要（terminal-notifier 等）

**技術スタック案:** Go + Bubble Tea + tmux API

### 案 2: Tauri + xterm.js デスクトップアプリ

xterm.js で PTY を描画し、Tauri でデスクトップアプリ化。

**メリット:**
- UI の自由度が最も高い（CSS で何でもできる）
- xterm.js は PTY 描画の実績豊富（VS Code のターミナルも xterm.js）
- ネイティブ通知が自然に使える
- クリック、ドラッグ、ホバー等のインタラクションが自由自在

**デメリット:**
- WebView 依存
- Tauri + Rust + TypeScript のスタック複雑さ
- ビルド・配布がやや面倒

**技術スタック案:** Tauri (Rust) + React/Solid + xterm.js

### 案 3: Web アプリ

ブラウザで動くアプリ。バックエンドがPTYを管理し、WebSocket で xterm.js に送る。

**メリット:**
- 案 2 と同じ UI 自由度
- インストール不要

**デメリット:**
- ブラウザのタブが1つ増える（本末転倒感）
- サーバープロセスが必要
- ブラウザ通知は弱い

### 案 4: 純 TUI（PTY を自前描画）

VT100 パーサを組み込んで TUI 内に PTY 出力を描画。

**メリット:**
- ターミナル完結、依存なし
- フル制御

**デメリット:**
- 実質ターミナルエミュレータの実装 → 開発コスト最大
- エスケープシーケンス対応のバグリスク

## 判断軸

| 優先度 | 項目 |
|--------|------|
| 高 | Claude Code の画面がそのまま見える |
| 高 | セッション一覧が見やすい（プロジェクト名、時間、状態） |
| 高 | 返信通知 |
| 中 | 開発コスト・スピード |
| 中 | 配布のしやすさ |
| 低 | ターミナル完結 |

## 決定

**案 1: tmux バックエンド + TUI フロントエンド** を採用。

理由:
- 特定のターミナルエミュレータに依存しない（汎用性）
- tmux に PTY 管理を任せて開発コストを抑える
- ユーザーのターミナル設定（フォント、カラー等）は外側のエミュレータが描画するのでほぼそのまま生きる

注意点:
- tmux のインストールが前提（ほとんどの開発者は入ってる）
- 色・マウスの透過設定は必要（`default-terminal`, `mouse on` 等）
